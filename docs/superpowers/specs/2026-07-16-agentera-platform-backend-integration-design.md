# AgentEra 平台后台真实资源接入设计

## 目标

在现有 Soybean 管理界面和 Payload BFF 骨架之上，逐页接入 AgentEra 的真实平台资源与真实业务操作，使后台从“页面和接口契约可运行”升级为“真实数据、权限、操作、审计闭环可用”。

本设计对应分支 `codex/platform-backend-integration`。`personal-dev` 保留为当前已验证并推送的 Soybean 后台基线。

## 当前事实

- Soybean 已提供正式管理入口、导航、角色能力控制和各业务页面。
- Payload 已提供登录、权限、审计、内容集合、Runtime 控制集合以及 AgentEra API BFF 骨架。
- 现有浏览器用例大量使用受控上游 fixture 验证页面和契约，不能替代真实 AgentEra API 联调。
- 平台真实资源、部分 mutation、高风险操作、审计完整性和生产容量验证尚未全部闭环。

因此，后续工作不再以“增加页面”为主，而以“把每一个页面接到唯一真实数据源”为主。

## 推荐架构

### Soybean

只负责管理交互、输入校验、状态展示和 capability 驱动的按钮可见性。前端不保存上游管理密钥，不直接访问 AgentEra API，也不复制业务规则。

### Payload BFF

负责管理员会话、角色与 capability 校验、参数白名单、敏感字段脱敏、请求 ID、审计和错误归一化。BFF 不持有充值、账户调度或计费领域的第二份状态。

### AgentEra API

继续作为平台用户、AI 资源、支付充值、用量、运营、安全和系统配置的业务事实源。若真实接口缺失，先记录契约缺口，再在 `agentera-claw-api` 建立一个窄分支补接口；不在 Payload 内临时复制业务实现。

### Runtime

Runtime 采用已实现的出站注册、心跳和命令领取协议。后台只展示 Runtime 实际上报的资源和 capability，只开放实例明确声明支持的命令。

数据流固定为：

```text
Soybean -> Payload BFF -> AgentEra API / Payload collections
Runtime -> Payload control endpoints -> Runtime collections -> Soybean
```

## 实施边界

### 第一阶段：真实接口盘点与只读接入

建立页面到真实接口的状态矩阵，标记为 `real`、`contract-only`、`missing-upstream` 或 `intentionally-disabled`。优先接通：

1. 平台用户与账户详情；
2. AI 账号、渠道、分组、代理与网络状态；
3. 订单、套餐、订阅、支付渠道只读信息；
4. 用量、请求、告警、风险和系统状态；
5. Runtime 实例、事件、命令和实际上报资源。

只读接口必须先真实可用，才开始 mutation。

### 第二阶段：普通业务操作

接通不需要二次认证的新增、编辑、启停、延期、取消、重试、公告和兑换码操作。每个操作必须具备：

- capability 校验；
- 参数白名单；
- 请求 ID 和上游请求 ID；
- 成功、失败和未知结果的明确状态；
- 服务端审计记录；
- 对应集成测试和浏览器测试。

### 第三阶段：高风险操作

退款、永久删除、支付密钥修改、数据库恢复、管理密钥重建以及 Runtime 高风险命令，统一使用一次性重新认证 grant、幂等键和目标绑定。未完成该机制前，相关操作继续隐藏或拒绝，不提供临时绕过入口。

### 第四阶段：生产验收

使用真实但可清理的测试账户完成端到端验收，覆盖权限矩阵、敏感字段泄漏扫描、大分页、超时、审计校验、备份和回滚。只有真实资源链路通过后，才能把对应模块标记为生产可用。

## 错误与安全约束

- 上游未配置返回 `not_configured`，不伪造空数据或成功状态。
- 上游超时与确定失败分开表达；mutation 超时不得自动重试。
- 管理密钥只存在服务端环境变量中，日志、审计、响应和浏览器存储不得出现明文。
- BFF 返回稳定错误码、中文操作提示和请求 ID，前端不得依赖上游原始错误结构。
- 任何真实 mutation 都必须审计；审计失败时高风险 mutation 不得静默继续。

## 测试策略

每个垂直业务切片遵循同一顺序：

1. 契约测试证明 AgentEra API 已提供所需接口；
2. BFF 集成测试证明权限、参数、脱敏、错误和审计；
3. Soybean 单元测试证明请求映射和状态处理；
4. 浏览器测试使用真实本地服务完成查询或可回滚 mutation；
5. 最后运行 Admin 全量集成、前端测试、类型检查、构建和代表性 E2E。

Fixture 只用于错误和边界条件，不再作为“真实资源已经接通”的验收证据。

## Git 策略

- 本仓库在 `codex/platform-backend-integration` 开发真实接入。
- 每个业务域形成独立、可验证、可回滚的提交。
- `agentera-claw-api` 仅在发现真实接口缺口时创建对应窄分支，不预先进行大规模重构。
- 不在该分支继续做无关的 Soybean 外观调整。
- 所有真实链路通过后，再决定合并回 `personal-dev`，不直接覆盖远程基线。

## 完成标准

某个后台模块只有同时满足以下条件，才算完成：

- 页面读取真实数据而不是 fixture、mock 或静态演示值；
- 页面允许的操作确实调用真实业务接口；
- 权限、脱敏、错误和审计均由服务端证明；
- 测试数据可回收，不污染正式业务数据；
- 集成测试和浏览器测试覆盖真实成功与失败路径；
- 运维文档记录所需配置、健康检查与回滚步骤。

整个后台只有在所有计划开放的模块都满足上述条件，并完成高风险与容量验收后，才标记为“生产完成”。
